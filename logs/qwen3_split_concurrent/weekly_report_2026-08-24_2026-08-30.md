# 周报

项目：`llama.cpp Qwen3 多请求调度与 QKV/KV Cache 机制分析`  
周期：`2026-08-24` 至 `2026-08-30`  
本周投入：`未统计`

## 1. 背景

本周围绕 Qwen3-1.7B BF16 在 `llama-server` continuous batching 场景下的多请求调度、QKV 生成、KV Cache 写入和 attention mask 隔离机制开展源码与日志复核，并将已有单文件/split GGUF 并发结果整理为可追溯报告。分析基于当前代码版本 `5ddcd411c`，没有修改推理源码。

本周使用两组互补证据：第一组是 `n_ctx=8192`、4 parallel slots 的并发性能实验，用于验证请求成功率、输出一致性和 wall time；第二组是 `n_ctx=512` 的受控 tensor trace，用于观察 Q/K/V、物理 KV slot、attention mask 和 logits shape。两组实验中的数值 `512` 含义不同：前者的 `n_ubatch=512` 是单图最大当前 token 数，后者 mask 第一维 `512` 是本轮 graph 读取的 padded KV span。

## 2. 动机与预期结果

开展本项工作的目标是把 server 调度、模型图和 KV Cache 三个层次连接起来，避免只根据接口日志推测内部张量行为。

- **现有问题：**普通 server 日志能显示 slot 进入、释放和请求 timing，但不能直接说明多个请求如何组成 flat batch，也不输出 Q/K/V、KV slot 或 mask tensor。
- **工作价值：**明确 `seq_id`、position、物理 slot、动态 KV span 与输出行之间的关系，可为并发正确性排查、KV Cache 优化和 backend 性能分析提供统一变量体系。
- **预期结果：**定位从 HTTP 请求到 graph compute 的关键函数，解释 join 阶段 `[512,24]` mask 与 Q/K/V shape 的来源，并区分标准 GGUF split 与真正的运行时 pipeline。

## 3. 探索框架与本周进展

本周按“调度入口 -> flat batch -> graph 构建 -> QKV 投影 -> KV 写入 -> masked attention -> logits -> 实验边界”的链路推进，使每项 shape 和结论都能回到源码或 trace。

### 3.1 机制与代码分析

- 梳理了 `server_queue::post()`、`process_single_task()`、`update_slots()`、`pre_decode()`、`llama_decode()`、`llama_context::process_ubatch()` 和 `llama_context::graph_compute()` 的执行关系。
- 确认 continuous batching 将多个 slot 的 token flat append 到一个 `llama_batch`；每个 token 携带 `position` 和 `seq_id=slot.id`，server 层不直接构造 Q/K/V。
- 跟踪 Qwen3 每层的 `build_qkv()`、Q/K head RMSNorm、RoPE、K/V Cache scatter、QK 点积、masked softmax、PV 加权和 output projection。
- 确认 Qwen3-1.7B 使用 GQA：`Hq=16`、`Hkv=8`、`D=128`，因此每两个 Q heads 共用一个 KV head。

关键代码链路为：

```text
HTTP request
  -> server task queue / slot
  -> flat llama_batch(token, position, seq_id, output)
  -> llama_decode()
  -> process_ubatch()
  -> model.build_graph()
  -> build_qkv()
  -> K/V 写入 KV Cache
  -> QK + mask + softmax + PV
  -> graph_compute()
  -> logits / sampler
```

### 3.4 结果分析

- **主要结果：**多请求不是分别构建 QKV 后再拼接，而是先形成 flat ubatch，再统一生成 `Q=[128,16,T]`、`K=[128,8,T]`、`V=[1024,T]`。join 阶段 `T=4+20=24`，因此完整 Q/K/V 分别为 `[128,16,24]`、`[128,8,24]` 和 `[1024,24]`。
- **KV Cache 结果：**join 前 `244=48+56+64+72+4` 个 cells；本轮旧请求使用 slots `244..247`，新请求使用 slots `248..267`，写后占用 `268`。`get_n_kv()` 至少按 256 对齐，因此 graph 使用 `C=512`，空 cell 由 mask 屏蔽。
- **请求隔离结果：**新请求第 `r` 个 query 只允许关注 slots `248..248+r`。旧请求 cells、未来位置和空 cells 均为 `-inf`，所以共享物理 KV buffer 不等于共享语义上下文。
- **非优势结果：**split GGUF 在三轮中在线时间均较短，但标准 loader 会把 shard 合并为一个 `llama_model` 和一张 Qwen3 graph；当前样本量和 mmap/系统状态不足以证明固有加速。
- **适用边界：**受控 trace 的 `[512,24]` 不能直接外推为 `n_ctx=8192` 并发实验每轮的固定 shape；实际 mask 第一维随 `used_max_p1` 以 256 粒度增长，直到物理 KV 容量上限。
